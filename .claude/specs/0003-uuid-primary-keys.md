# SPEC — Clés primaires UUID v7 sur toutes les entités (phase A du réordonnancement)

> Statut : **design validé en session le 2026-09-14**, à découper en tâches.
> Prérequis de la spec 0004 (réordonnancement des contenus par glisser-déposer), livré **seul**
> dans une release dédiée : la migration réécrit les clés primaires de tables qui ont des données
> en production et n'est pas réversible.
>
> ⚠️ **Ce fichier vit dans un dépôt public** (`.claude/` est versionné, hors `CLAUDE.local.md`).
> Aucun secret, aucune adresse réelle, aucun nom de compte. Voir le journal d'audit en §10.

---

## 1. Objectif

Toutes les entités du projet sont identifiées par un entier auto-incrémenté (`GENERATED BY DEFAULT
AS IDENTITY`), assigné par PostgreSQL au `flush`. Règle nouvelle, décidée le 2026-09-14 et
applicable **à tout le projet dès maintenant** : **toute entité porte une clé primaire UUID v7,
posée par son constructeur**. Cette spec fait passer les 14 entités existantes, leurs chemins
d'API, leurs tests et le frontend, en une seule livraison.

### Le vrai sujet de démonstration

Une entité qui connaît son identité avant d'être persistée est une entité que l'on construit, teste
et compare sans base de données : c'est le style DDD que le projet revendique. Le v7, ordonné dans
le temps, conserve la localité d'index et le sens des tris de repli `ORDER BY id` que les repositories
utilisent déjà. Et une migration irréversible sur des tables peuplées est l'occasion de montrer la
discipline de livraison du projet : passage préprod obligatoire, preuve avant promotion.

### Public visé

Aucun changement visible pour le visiteur ni pour les paliers `ROLE_USER`/`ROLE_TRUSTED` : aucun
contrat public n'expose d'`id`. Seul le backoffice (`ROLE_SUPER`) voit ses identifiants changer de
forme dans les URLs et les DTO.

### Hors périmètre

- Les groupes de traduction, l'endpoint d'ordre et le glisser-déposer : spec 0004.
- Les tables qui ne sont pas des entités du projet (Messenger, rate limiter, migrations).
- Un Value Object d'identité par entité (`IncidentId`…) : `Symfony\Component\Uid\Uuid` est déjà un
  Value Object ; quatorze wrappers que la couche API déballerait aussitôt n'apporteraient rien.
- Un test automatisé de la migration de données : le projet n'en a pas, la preuve est le passage
  préprod (§8).

## 2. Décisions structurantes

- **D1 — UUID v7, généré dans le constructeur de l'entité.** `#[ORM\Id] #[ORM\Column(type:
  UuidType::NAME)] private Uuid $id;` sans `GeneratedValue`, `$this->id = Uuid::v7();` en tête de
  constructeur, `getId(): Uuid` non nullable. Alternative écartée : `#[ORM\CustomIdGenerator]`
  Doctrine, qui n'assigne qu'au `persist` et garde `getId()` nullable — précisément ce que l'on veut
  supprimer.
- **D2 — Type PostgreSQL `uuid` natif** via le `UuidType` de `symfony/doctrine-bridge` (déjà
  disponible), jamais `VARCHAR(36)` : 16 octets, comparaison native, index compacts.
- **D3 — `symfony/uid` devient une dépendance directe** (`8.1.*`, comme les autres composants
  Symfony du projet), et non plus seulement transitive.
- **D4 — Des migrations irréversibles, une par tâche backend** (amendé au découpage du 2026-09-14 :
  la CI construit la base de test par `doctrine:migrations:migrate`, donc une tâche n'est verte que si
  elle embarque la migration de ses propres tables ; cinq migrations jouées d'un bloc à la release
  valent une seule pour le déploiement). Chaque `down()` appelle
  `$this->throwIrreversibleMigrationException()` : les entiers d'origine ne sont pas restituables et
  un rollback qui les réinventerait mentirait. Conséquence assumée : la release passe par préprod
  avec vérification réelle avant promotion (invariant existant pour tout ce qui touche un volume
  initialisé).
- **D5 — Les UUID des lignes existantes sont v7 et monotones dans l'ordre des anciens ids.**
  PostgreSQL 18 (`POSTGRES_TAG=18.6-alpine`) fournit `uuidv7(interval)` ; chaque ligne reçoit
  `uuidv7()` décalé de son rang (en millisecondes) dans l'ordre de l'ancien `id`, de sorte que deux
  lignes à position égale gardent exactement l'ordre qu'elles ont aujourd'hui. `gen_random_uuid()`
  (v4) a été écarté : il aurait rendu ce tri de repli aléatoire.
- **D6 — Un `{id}` malformé est un 404 du routeur, pas un cas du Provider.** Chaque opération
  d'item déclare `requirements: ['id' => Requirement::UUID]` (`Symfony\Component\Routing\Requirement`).
  Le trait `ResolvesUriVariables` remplace `uriVariableInt()` par `uriVariableUuid(): Uuid` (avec
  `assert(Uuid::isValid(...))` en garde de second niveau). Ce `requirements` est aussi ce qui, en
  spec 0004, empêchera `PUT …/order` d'être capturé par `PUT …/{id}`.
- **D7 — Les DTO exposent l'id en `string` RFC 4122**, `fromEntity` convertit par
  `$entity->getId()->toRfc4122()`. Le domaine manipule `Uuid`, la frontière HTTP manipule des
  chaînes ; le frontend type `id: string` et n'en fait jamais rien d'autre qu'une clé ou un segment
  d'URL.

### Contrats vérifiés (2026-09-14, dans le code, pas de mémoire)

- `symfony/doctrine-bridge` du projet fournit `Types/UuidType.php` (`UuidType::NAME = 'uuid'`).
- `symfony/routing` fournit `Requirement::UUID` (toutes versions) ; on ne restreint pas à
  `UUID_V7` : les tests fonctionnels doivent pouvoir forger un UUID quelconque.
- `ApiRouteExposureTest` remplace les paramètres de route par un placeholder (`'1'` par défaut,
  `preg_replace_callback` ligne ~408). Avec D6, `/api/backoffice/incidents/1` répondrait 404 par le
  `RouterListener` (priorité 32) **avant** le firewall (priorité 8), et le test perdrait sa portée
  sur toutes les routes d'item. Le placeholder de `{id}` devient un UUID fixe ; c'est la seule
  modification autorisée sur ce test, et elle ne touche ni `PUBLIC_PATHS` ni `BASE_TIER_PATHS`.
- Une seule clé étrangère entre entités : `password_setup_token.user_id → cpg_user.id`
  (`ON DELETE CASCADE`).
- `SendAccountInvitationMessage` transporte `int $userId` (oublié par la rédaction initiale) : il
  passe en `string` RFC 4122 ; un message encore en file au déploiement serait rejoué avec un
  entier, d'où la vérification `messenger:failed:show` avant la release (§8).

## 4. Critères d'acceptation

### A2 — Entités

- `new Incident(...)` (et chacune des 13 autres) expose immédiatement un `getId()` de type `Uuid`,
  version 7, sans `persist` ni `flush`.
- Deux constructions successives donnent deux ids distincts et **croissants** (comparaison de
  `toRfc4122()`), ce qui pin le v7 et non un v4.
- `PasswordSetupToken::getUser()->getId()` est l'`Uuid` du `CpgUser`, la relation `ManyToOne` reste
  `nullable: false`, `onDelete: 'CASCADE'`.

### A3 — Migration

- Sur une base de dev peuplée par les seeds, plus un compte invité (pour la FK) : après migration, chaque table a
  une colonne `id uuid NOT NULL` en clé primaire, aucune colonne entière résiduelle, et
  `password_setup_token.user_id` est `uuid` avec sa FK `ON DELETE CASCADE` recréée.
- Pour toute table, l'ordre `ORDER BY id` après migration est l'ordre `ORDER BY id` d'avant (D5).
- `doctrine:schema:validate` ne signale aucune divergence entre mapping et schéma.
- `down()` lève `IrreversibleMigration` ; `doctrine:migrations:migrate prev` échoue explicitement.

### A4 — API

- `GET /api/backoffice/incidents/{id}` avec l'UUID d'une entrée → 200, avec un UUID inexistant →
  404 (`IncidentNotFoundException`, mapping existant), avec `1` ou `abc` → 404 **sans** atteindre le
  Provider (test : un Provider espion n'est pas appelé, ou plus simplement le 404 est celui du
  routeur et non un problem+json applicatif).
- Les `id` des collections backoffice sont des chaînes RFC 4122 ; aucune réponse ne contient un `id`
  numérique.
- `ApiRouteExposureTest` : les trois invariants (anonyme → 401/403 partout hors allow-list ; rien de
  `/api/backoffice` n'est allow-listé ; le backoffice refuse un compte sans `ROLE_SUPER`) restent
  verts, avec pour seule modification le placeholder UUID de `{id}`.
- Le flux d'invitation complet (invite → message Messenger → token → `GET/POST
  /api/account/password-setup/{token}`) reste vert : c'est le seul chemin qui traverse la FK.

### A5 — Frontend

- Aucun `id: number` ne subsiste sous `src/domain/admin`, `src/application/admin`,
  `src/infrastructure/admin`, `src/presentation/pages/admin` (grep vide).
- `AdminUsersPage.vue` continue de désactiver les boutons de la ligne du compte courant par
  `username`, pas par id : inchangé, vérifié.
- `vue-tsc -b` ne signale aucune erreur ; aucun `parseInt`, `Number()` ou comparaison numérique sur
  un id.

## 7. Style de code

- Conventions du projet sans exception : `declare(strict_types=1)`, typage complet, PHPStan `max`
  sans baseline, Rector et Psalm verts.
- La migration est **écrite à la main** et commentée : ce que `make:migration` génère (un
  `ALTER COLUMN … TYPE uuid` impossible sans `USING`) n'est qu'un point de départ. Elle procède
  table par table, dans un ordre fixe : colonne `uuid` ajoutée, remplie (D5), FK et PK retirées,
  anciennes colonnes supprimées, renommage, PK et FK recréées.
- Les tests d'entité remplacent `assertNull($x->getId())` par une assertion sur `Uuid::isValid` et
  la version 7 ; pas de `assertInstanceOf` seul, qui laisserait passer un v4.
- Frontend : les specs utilisent des UUID littéraux constants (`const INCIDENT_ID = '0192…'`),
  jamais un générateur, pour rester déterministes et lisibles.

## 8. Stratégie de test

- **Unitaires** : chaque entité (id v7, croissance), `ResolvesUriVariables::uriVariableUuid` (valide,
  invalide → assertion).
- **Fonctionnels** : toutes les suites existantes, sur `getId()->toRfc4122()` ; un cas « `{id}` non
  UUID → 404 » par ressource backoffice ; le flux d'invitation de bout en bout.
- **Migration** : jouée en dev sur une base peuplée par les seeds et une invitation
  (critères A3), puis sur préprod. La preuve de production est le passage préprod : `rollout
  status` du Deployment, logs du Job `migrate` sans erreur, puis vérification manuelle d'une
  ressource backoffice (liste, édition, suppression) et d'une invitation.
- **Frontend** : les 26 specs existantes adaptées ; aucun nouveau comportement, donc aucun nouveau
  test au-delà des types.
- **Sécurité** : `ApiRouteExposureTest` et `AccessControlAnchoringTest` verts.

## 9. Limites

### Toujours

- Poser l'id dans le constructeur ; jamais un `setId()`, jamais un id fourni de l'extérieur pour une
  création (les seeds et les fixtures n'en ont pas besoin).
- `requirements: ['id' => Requirement::UUID]` sur **toute** nouvelle opération d'item, dès sa
  déclaration.
- Vérifier `debug:router` après modification d'une ressource (règle existante).

### Demander avant

- Introduire une entité sans UUID, quelle qu'en soit la raison.
- Exposer un id d'entité dans un contrat public (aujourd'hui aucun ne le fait ; un v7 révèle
  l'instant de création, anodin pour du contenu de démonstration, à peser pour autre chose).
- Toucher `ApiRouteExposureTest` au-delà du placeholder.

### Jamais

- Un `down()` qui prétend restaurer les entiers.
- Promouvoir en prod sans le passage préprod décrit en §8.
- Un `VARCHAR(36)` pour un UUID.
